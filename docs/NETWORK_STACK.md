## 2. L3 — IP: адресация, маршрутизация, DNS

Сетевой уровень отвечает за то, чтобы пакет, отправленный в одной точке интернета, попал в другую. В нашем проекте он представлен протоколом IPv4 и вспомогательными службами — DNS для разрешения имён и ICMP для служебных сообщений.

### 2.1. IPv4-адресация VPS

Виртуальный сервер имеет публичный IPv4-адрес `<YOUR_VPS_IP>`. Этот адрес — точка входа для всего внешнего трафика: туда подключаются VPN-клиенты на 443/2096, туда же стучится браузер админа на 4443, и там же слушается 22 для SSH.

На самом VPS работает несколько сетевых интерфейсов:

```
eth0   <YOUR_VPS_IP>/24   ← публичный, смотрит в интернет
lo     127.0.0.1/8         ← loopback, для межпроцессного взаимодействия
```

Распределение сервисов по интерфейсам важно для безопасности. Xray слушает на `0.0.0.0:443` и `0.0.0.0:2096` (VPN-порты) — это значит «на всех интерфейсах», включая публичный. А gRPC-API статистики слушает на `127.0.0.1:10085` — только loopback, снаружи недоступен. Тот же принцип для FastAPI-админки: сам процесс слушает `127.0.0.1:8001`, а наружу его «выставляет» nginx через `proxy_pass http://127.0.0.1:8001`.

В конфиге Xray мы видим два варианта:

```json
// server/xray-server.json
{
  "tag": "api-in",
  "listen": "127.0.0.1",     ← API — только локально
  "port": 10085
},
{
  "tag": "vless-reality-vision",
  "listen": "0.0.0.0",        ← VPN — на всех интерфейсах
  "port": 443
}
```

Разница между `0.0.0.0` и `127.0.0.1` — это не адрес назначения, а *на каких адресах сокет принимает входящие соединения*. `0.0.0.0` означает «bind ко всем локальным IP», `127.0.0.1` — «только к loopback». Это первичный механизм защиты внутренних сервисов.

### 2.2. Маршрутизация: от клиента до VPS, от VPS до целевого сервера

Когда VPN-клиент на мобильном телефоне отправляет пакет на `<YOUR_VPS_IP>:443`, этот пакет проходит длинный путь:

```
[Телефон]
   │ Wi-Fi/LTE канал
   ▼
[Маршрутизатор провайдера]    ← source IP телефона, dest <YOUR_VPS_IP>
   │ BGP-маршрутизация по AS
   ▼
[Магистральный провайдер (Tier-1)]
   │
   ▼
[Транзитная AS ← граница страны/континента]
   │
   ▼
[Дата-центр хостера, куда арендован VPS]
   │ внутренний свитч
   ▼
[VPS <YOUR_VPS_IP>]
```

Маршрутизация в Интернете основана на протоколе **BGP** (Border Gateway Protocol) — между автономными системами (AS) провайдеров. Внутри одной AS используется **OSPF** или **IS-IS**. Это всё работает «под капотом» и приложением не управляется.

На VPS используется стандартная таблица маршрутизации Linux:

```
$ ip route
default via 157.22.176.1 dev eth0        ← default gateway (шлюз хостера)
157.22.176.0/24 dev eth0 proto kernel scope link src <YOUR_VPS_IP>
127.0.0.0/8 dev lo proto kernel scope host src 127.0.0.1
```

Default gateway `157.22.176.1` — это маршрутизатор хостера, через который уходят все пакеты в интернет. Когда Xray инициирует исходящее соединение к целевому серверу (например, к `www.youtube.com:443` по поручению VPN-клиента), он отправляет TCP SYN через `eth0` на этот шлюз, и дальше оно идёт по BGP.

### 2.3. DNS — разрешение имён

В проекте участвуют следующие DNS-имена:

| Имя | Тип записи | Значение | Где используется |
|---|---|---|---|
| `<YOUR_DOMAIN>` | A | `<YOUR_VPS_IP>` | админка, ACME |
| `<MASKED_SNI_HOST>` | A | некий IP (меняется) | Reality: dest для обычного TLS-handshake |
| `api.telegram.org` | A | группа IP (round-robin) | Telegram Bot API |

**Как работает DNS.** Клиент (например, curl или браузер) вызывает системный резолвер (`getaddrinfo` на Linux, аналоги на iOS/Android). Резолвер идёт к локальному DNS-серверу (обычно — 1.1.1.1, 8.8.8.8 или DNS провайдера), тот отправляет итеративные запросы: сначала в root-зону (`.`), получает NS для `.ru`, дальше — NS для `fvds.ru`, и в конце — A-запись для `<YOUR_DOMAIN>`.

```
Клиент                Локальный резолвер            Root → TLD → Authoritative
  │                         │                              │
  │── запрос A <YOUR_DOMAIN> (UDP :53) ──►          │
  │                         │                              │
  │                         │── .         (NS для .ru) ──► │
  │                         │◄─ NS=a.dns.ripn.net          │
  │                         │                              │
  │                         │── .ru       (NS для fvds.ru) ──►
  │                         │◄─ NS=ns1.fvds.ru             │
  │                         │                              │
  │                         │── fvds.ru   (A <your_subdomain>) ──►
  │                         │◄─ A <YOUR_VPS_IP>           │
  │                         │                              │
  │◄─ A <YOUR_VPS_IP> ─────                               │
```

**TTL (Time To Live).** Каждая DNS-запись содержит TTL в секундах — сколько ответ можно кэшировать. Это компромисс:
- высокий TTL (86400 с) — экономим на запросах, но смена IP распространяется сутки;
- низкий TTL (60 с) — оперативная смена IP, но больше нагрузка на DNS.

Для `fvds.ru` по умолчанию TTL ~3600 секунд (час). Когда мы впервые выпускаем сертификат через ACME, Let's Encrypt делает DNS-запрос, чтобы убедиться, что домен действительно резолвится в наш IP. Если запись только что добавлена и кэшируется у провайдера LE со старым значением, придётся ждать TTL.

**DNS-over-TLS / DNS-over-HTTPS.** В некоторых сетях DNS-запросы тоже перехватываются. Современные системы поддерживают DoT (:853) и DoH (HTTPS :443) — шифрованный DNS. В нашем проекте явно не настроен, используется системный резолвер — провайдер видит имя `<MASKED_SNI_HOST>` в запросе Xray при запуске. Но так как Xray один раз разрешает имя и дальше работает по IP, это одноразовое событие.

### 2.4. ICMP

Протокол служебных сообщений. Используется для:
- `ping` — проверка достижимости (Echo Request / Echo Reply);
- `traceroute` — выявление цепочки маршрутизаторов (TTL-exceeded);
- `Fragmentation Needed` — уведомление об ограничении MTU;
- `Destination Unreachable` — порт/хост недоступен.

В проекте ICMP не управляется кодом, но важен для диагностики. Если `ping <YOUR_VPS_IP>` не доходит — скорее всего, хостер блокирует ICMP (многие блокируют, это нормально) или VPS выключен. Если `traceroute` виден до какого-то хопа и дальше пропадает — проблема на промежуточном маршрутизаторе.

### 2.5. Почему IPv6 не используется

Мы используем только IPv4. В nginx есть `listen [::]:80` и `listen [::]:4443 ssl http2` — это на случай, если хостер предоставит IPv6. Но сейчас у VPS `<YOUR_VPS_IP>` IPv6 не настроен. Большинство публичных хостеров выдают IPv6-подсеть по запросу; у нас её нет. Это не создаёт проблем, потому что VPN-клиенты всё равно резолвят `<YOUR_DOMAIN>` в A-запись.

## 3. L4 — TCP: надёжный транспорт

Транспортный уровень отвечает за то, чтобы поток байт между двумя процессами доехал целым, в порядке, без потерь и дубликатов. В нашем проекте это везде TCP — от публичных портов VPN до внутренних `proxy_pass`-ов.

### 3.1. Почему TCP, а не UDP

Вопрос закономерный: современные VPN (WireGuard) работают по UDP, QUIC/HTTP/3 — тоже UDP. Почему у нас весь стек на TCP?

**Причины выбора TCP в нашем проекте:**

1. **Маскировка под веб-трафик.** Reality-транспорт имитирует обычный HTTPS к внешнему домену. HTTPS работает по TCP :443 — и наш VPN тоже работает по TCP :443. Если бы мы слушали UDP :443, DPI-анализатор заметил бы аномалию: HTTPS к обычным сайтам через UDP :443 (QUIC) ещё не повсеместен, а на нашем IP *весь* трафик был бы QUIC-like — это уже паттерн.
2. **Гарантия доставки.** VLESS и HTTP/2 полагаются на надёжный транспорт. Их собственные механизмы сверху TCP не дублируют retransmit. Если пустить их по UDP, пришлось бы реализовывать TCP-подобные свойства на уровне приложения (что и делает QUIC).
3. **Простота прохождения через NAT и firewall.** Многие корпоративные и мобильные сети режут UDP или применяют агрессивный NAT-timeout. TCP-соединения удерживаются намного дольше, state-машина NAT понимает `SYN/ACK/FIN`.
4. **Для WebSocket и HTTP/2 альтернативы нет.** WebSocket — это апгрейд поверх HTTP, а HTTP классический — TCP-ориентированный. Только HTTP/3 работает по QUIC/UDP, и то это про отдельный транспорт.

**Где UDP всё-таки нужен.** В нашем проекте UDP явно не открыт ни на одном порту (проверяется `ss -ulnp`). Исключение — DNS-запросы изнутри VPS наружу (это UDP :53), но это исходящие пакеты, не входящий listen.

### 3.2. TCP handshake (трёхэтапное рукопожатие)

Любое TCP-соединение начинается с классического handshake:

```
Клиент                                                 Сервер
  │                                                       │
  │── SYN, seq=X ──────────────────────────────────────► │
  │                                                       │
  │◄─────────────────── SYN-ACK, seq=Y, ack=X+1 ──────── │
  │                                                       │
  │── ACK, seq=X+1, ack=Y+1 ───────────────────────────► │
  │                                                       │
  │            → соединение ESTABLISHED ←                 │
  │                                                       │
  │═══════════════ обмен данными ═══════════════════════│
```

**Шаг 1 (SYN).** Клиент отправляет сегмент с флагом SYN (Synchronize) и начальным sequence number (обычно случайное 32-битное число). Это запрос на открытие соединения.

**Шаг 2 (SYN-ACK).** Сервер, если он слушает порт, отвечает с флагами SYN+ACK: подтверждает получение клиентского SYN (ack=X+1) и отправляет свой seq=Y.

**Шаг 3 (ACK).** Клиент подтверждает SYN сервера, отправляя ACK с ack=Y+1.

После этого соединение в состоянии ESTABLISHED с обеих сторон, можно передавать данные.

**Зачем три шага, а не два?** Чтобы обе стороны убедились, что они:
1. Согласовали начальные sequence numbers.
2. Находятся в ESTABLISHED одновременно.
3. Обе могут передавать данные.

Если бы был только SYN + ACK, сервер не знал бы, что клиент уверенно принял его seq.

**Состояния TCP-коннекшна** (упрощённо):

```
      CLOSED
        │ connect()                   listen()
        ▼                                 │
      SYN_SENT                            ▼
        │ получил SYN-ACK              LISTEN
        │ отправил ACK                    │ получил SYN
        ▼                                 │ отправил SYN-ACK
     ESTABLISHED ◄────────────────► SYN_RCVD
        │                                 │ получил ACK
        │                                 ▼
        │                            ESTABLISHED
        │
        │ close() или FIN
        ▼
      FIN_WAIT_1 / CLOSE_WAIT
        │
        ▼
      FIN_WAIT_2 / LAST_ACK
        │
        ▼
       TIME_WAIT (2*MSL)
        │
        ▼
      CLOSED
```

### 3.3. Keep-alive: зачем и как

TCP keep-alive — это механизм, при котором по длинному простаивающему соединению периодически посылаются пустые ACK-пробы. Если несколько проб подряд не получают ответа, соединение считается мёртвым.

Настраивается на уровне сокета (Linux):

```
/proc/sys/net/ipv4/tcp_keepalive_time    = 7200 сек (2 часа до первой пробы)
/proc/sys/net/ipv4/tcp_keepalive_intvl   = 75 сек  (интервал между пробами)
/proc/sys/net/ipv4/tcp_keepalive_probes  = 9       (число проб до считать мёртвым)
```

**Почему это важно для WebSocket в нашем проекте.** Наш веб-интерфейс использует WebSocket на `/ws/stats` (см. `web/routes_ws.py`), по которому сервер пушит клиенту статистику трафика. Это долгоживущее соединение — оно может простаивать десятки минут, пока админ не обновляет страницу.

Между клиентом и сервером часто стоит NAT-маршрутизатор (у мобильного оператора, домашнего роутера, корпоративного firewall). NAT-таблица хранит трансляцию адресов только пока соединение активно. При простое таблица истекает (обычно 30–300 секунд для TCP), и следующий пакет клиента не дойдёт до сервера — коннекшн «обрывается без FIN».

Чтобы этого не было, у нас два механизма:

1. **Системный TCP keep-alive** — раз в 2 часа (по умолчанию) посылает пробу. Не спасает от NAT с 5-минутным таймаутом.
2. **Прикладной heartbeat в WebSocket** — в `web/routes_ws.py` есть `_heartbeat_loop`, который раз в 30 секунд отправляет JSON-сообщение `{"type": "ping", "ts": ...}`:

```python
# web/routes_ws.py
HEARTBEAT_INTERVAL_SEC = 30.0

async def _heartbeat_loop(ws: WebSocket) -> None:
    while True:
        await asyncio.sleep(HEARTBEAT_INTERVAL_SEC)
        await ws.send_text(json.dumps({"type": "ping", "ts": time.time()}))
```

Это гарантирует, что каждые 30 секунд по соединению реально идёт байт, NAT-state обновляется, и соединение остаётся живым.

Также в nginx мы явно задали длинные таймауты для `/ws/`:

```nginx
# deploy/nginx-lockdown.conf
location /ws/ {
    proxy_read_timeout 3600s;   ← nginx не будет резать idle-коннект в течение часа
    proxy_send_timeout 3600s;
}
```

Без этого nginx по умолчанию закрывает соединение через 60 секунд простоя.

### 3.4. TIME_WAIT: что это и почему иногда мешает

После close() инициирующая сторона входит в состояние TIME_WAIT, где держит сокет занятым 2×MSL (обычно 60–120 секунд на Linux). Это нужно, чтобы:
- запоздалые дубликаты старого соединения не «вошли» в новое с теми же (ip:port / ip:port);
- FIN-ACK гарантированно получил противоположную сторону.

На практике при интенсивном создании соединений (например, нагрузочный тест) TIME_WAIT копятся и забивают локальные порты. Лечится:
- `SO_REUSEADDR` на сокете;
- `net.ipv4.tcp_tw_reuse = 1`;
- оптимизацией клиента, чтобы переиспользовать коннекты (keep-alive).

В нашем проекте TIME_WAIT не проблема — нагрузка небольшая.

### 3.5. Congestion control и MSS

TCP автоматически подбирает скорость отправки под пропускную способность канала. Алгоритмы: Reno, Cubic (дефолт в Linux), BBR (новый, у Google). На Linux управляется через:

```
sysctl net.ipv4.tcp_congestion_control = cubic
```

Для VPN-туннелей имеет значение MSS (Maximum Segment Size). Если мы упаковываем TCP внутри TLS внутри TCP (как в VLESS/Reality), каждый слой заголовков уменьшает полезный payload. Типичная цепочка:

```
Ethernet MTU          = 1500 байт
- IP header           = 20  → 1480
- TCP header          = 20  → 1460  ← это MSS наружу
- TLS record header   = 5   → 1455
- Reality overhead    = ~32 → ~1423
- VLESS header        = ~16 → ~1407
- inner TCP/IP        = 40  → ~1367
```

Если где-то в цепочке есть PMTU-проблема (например, на мобильном операторе), пакеты начинают фрагментироваться, что ломает производительность. Поэтому важно, чтобы Path MTU Discovery работал — а для этого ICMP fragmentation-needed не должен блокироваться.

## 4. L5/L6 — TLS 1.2 и 1.3

Слои сессии и представления в нашей архитектуре закрывает TLS. Он стоит между TCP и прикладным протоколом и обеспечивает:
- **конфиденциальность** — шифрование трафика симметричным ключом;
- **аутентичность сервера** — проверка, что мы соединились с тем, с кем собирались (сертификат);
- **целостность** — обнаружение модификаций (MAC/AEAD-тег);
- **опционально** — аутентичность клиента (mTLS, у нас не используется).

В проекте TLS работает в нескольких местах:

1. **nginx на :4443** — TLS-терминация для веб-админки (сертификат Let's Encrypt).
2. **Xray на :443 и :2096** — Reality (кастомизированный TLS) для VPN.
3. **Telegram Bot API** — клиентский TLS к `api.telegram.org:443`.
4. **ACME-клиент** — TLS к `acme-v02.api.letsencrypt.org:443`.

### 4.1. Версии TLS

TLS 1.0 и 1.1 давно признаны небезопасными и отключены. В проекте конфиг nginx задаёт:

```nginx
# deploy/nginx-lockdown.conf:23
ssl_protocols       TLSv1.2 TLSv1.3;
ssl_ciphers         HIGH:!aNULL:!MD5;
ssl_prefer_server_ciphers on;
```

**`ssl_protocols TLSv1.2 TLSv1.3`** — разрешаем только эти две версии. TLSv1.2 оставлен для совместимости со старыми клиентами (старые Android, IE, embedded). Основной поток идёт по TLSv1.3.

**`ssl_ciphers HIGH:!aNULL:!MD5`** — используются только «высокостойкие» шифры. Исключены:
- `!aNULL` — шифры без аутентификации (anonymous DH);
- `!MD5` — шифры с хэшем MD5, он давно сломан.

Фактически в TLS 1.3 этот параметр почти не действует — там фиксированный набор AEAD-шифров. Он важнее для TLS 1.2.

**`ssl_prefer_server_ciphers on`** — при согласовании шифра приоритет имеет порядок сервера, а не клиента. Это позволяет администратору форсировать хорошие шифры, даже если клиент отдаёт предпочтение слабым.

### 4.2. Handshake TLS 1.3 (подробно)

TLS 1.3 (RFC 8446) — это упрощённый и более быстрый handshake по сравнению с 1.2. Суть: один полный RTT до получения прикладных данных.

```
Клиент                                                    Сервер
  │                                                           │
  │ 1. ClientHello:                                           │
  │    - supported_versions: [TLS 1.3, TLS 1.2]              │
  │    - cipher_suites: [TLS_AES_256_GCM_SHA384, ...]        │
  │    - key_share: [X25519 public, P-256 public]            │
  │    - signature_algorithms: [ecdsa_secp256r1_sha256, ...] │
  │    - server_name (SNI): "<YOUR_DOMAIN>"           │
  │    - extensions: ALPN, session_ticket, ...               │
  │────────────────────────────────────────────────────────► │
  │                                                           │
  │                                                           │ сервер выбирает
  │                                                           │ cipher suite,
  │                                                           │ группу ключа,
  │                                                           │ извлекает сертификат
  │                                                           │
  │ 2. ServerHello:                                           │
  │    - selected_version: TLS 1.3                            │
  │    - cipher_suite: TLS_AES_256_GCM_SHA384                │
  │    - key_share: X25519 public                             │
  │◄──────────────────────────────────────────────────────── │
  │                                                           │
  │  ─── с этого момента всё ШИФРУЕТСЯ handshake-ключом ───  │
  │                                                           │
  │ 3. EncryptedExtensions (доп. параметры):                  │
  │    - ALPN: h2                                             │
  │◄──────────────────────────────────────────────────────── │
  │                                                           │
  │ 4. Certificate (X.509 цепочка):                           │
  │    - leaf: CN=<YOUR_DOMAIN>, issuer=R3            │
  │    - intermediate: R3                                     │
  │    - (root ISRG Root X1 — не отправляется, он в trust)   │
  │◄──────────────────────────────────────────────────────── │
  │                                                           │
  │ 5. CertificateVerify:                                     │
  │    - подпись хэша handshake приватным ключом сервера     │
  │    - доказывает, что у сервера есть соответствующий      │
  │      приватный ключ к сертификату                        │
  │◄──────────────────────────────────────────────────────── │
  │                                                           │
  │ 6. Finished (HMAC всех handshake-сообщений):              │
  │    - подтверждает целостность handshake                   │
  │◄──────────────────────────────────────────────────────── │
  │                                                           │
  │ → клиент ПРОВЕРЯЕТ:                                       │
  │   - сертификат валиден (цепочка до trusted root)          │
  │   - имя в сертификате соответствует SNI                   │
  │   - текущая дата внутри NotBefore..NotAfter               │
  │   - CertificateVerify подпись валидна                     │
  │                                                           │
  │ 7. Finished (клиентский):                                 │
  │────────────────────────────────────────────────────────► │
  │                                                           │
  │ 8. Application Data (первый HTTP-запрос):                │
  │════════════════════════════════════════════════════════► │
  │                                                           │
  │ 9. Application Data (HTTP-ответ):                         │
  │◄════════════════════════════════════════════════════════ │
```

**Почему handshake занимает 1 RTT.** Клиент отправляет ClientHello с key_share — своей долей эфемерного DH. Сервер в одном ответном flight'е присылает ServerHello, свой key_share, сертификат, подпись и Finished. После этого сервер уже может отправить Application Data. Клиент только подтверждает Finished и тоже шлёт Application Data.

В TLS 1.2 handshake был двумя RTT: сначала обмен Hello, потом обмен ключами, и только потом Finished.

### 4.3. 0-RTT в TLS 1.3

Если клиент уже общался с сервером раньше, он может положить в первый flight к серверу `early_data` — зашифрованные прикладные данные на основе pre-shared key. Это 0 RTT. Но у 0-RTT есть проблема — replay-attack, поэтому он применим только к идемпотентным запросам (GET без побочных эффектов). В nginx это включается директивой `ssl_early_data on`, у нас не включено.

### 4.4. Отличия TLS 1.3 от TLS 1.2

| Аспект | TLS 1.2 | TLS 1.3 |
|---|---|---|
| Handshake RTT | 2 RTT | 1 RTT (0 RTT с PSK) |
| Cipher suites | 37+ вариантов, много устаревших | 5 AEAD-шифров, все современные |
| RSA key exchange | Разрешён (но опасен — нет forward secrecy) | Удалён, только (EC)DHE |
| Статический DH | Разрешён | Удалён, только эфемерные ключи |
| MD5, SHA-1 | Частично | Запрещены |
| CBC-шифры | Разрешены | Запрещены (только AEAD: AES-GCM, ChaCha20-Poly1305) |
| Compression | Возможна (но CRIME-атака) | Запрещена |
| Renegotiation | Разрешена | Удалена, заменена на key update |
| Защита handshake | Часть в cleartext (cert, ext) | Весь handshake с EncryptedExtensions шифруется |
| Downgrade-protection | Частичная | Явный anti-downgrade в ServerRandom |

**Forward secrecy** — ключевое свойство современного TLS: если злоумышленник записал трафик и позже получил приватный ключ сервера, расшифровать старый трафик он всё равно не сможет, потому что сессионный ключ выводится из эфемерного DH, который удаляется сразу после handshake.

### 4.5. Цепочка сертификатов

В TLS X.509-сертификат — это документ, подписанный центром сертификации (CA). Для домена `<YOUR_DOMAIN>` выпущен сертификат Let's Encrypt:

```
Root CA: ISRG Root X1                    ← предустановлен в ОС/браузерах
  └── Intermediate CA: R3                ← подписан ISRG Root X1
        └── Leaf: CN=<YOUR_DOMAIN> ← подписан R3
```

nginx отдаёт клиенту `fullchain.pem` — это конкатенация leaf + intermediate:

```nginx
# deploy/nginx-lockdown.conf:20-21
ssl_certificate     /etc/letsencrypt/live/<YOUR_DOMAIN>/fullchain.pem;
ssl_certificate_key /etc/letsencrypt/live/<YOUR_DOMAIN>/privkey.pem;
```

Клиент получает цепочку, находит у себя в trust-store ISRG Root X1, идёт вверх по цепочке и проверяет каждую подпись. Если все подписи валидны, цепочка достроена до доверенного корня, имя в leaf соответствует SNI и даты в норме — сертификат считается доверенным.

**Самоподписанный сертификат** — это сертификат, где leaf подписан сам собой, без CA. Браузер показывает предупреждение `NET::ERR_CERT_AUTHORITY_INVALID`, потому что:
- подписи нет у доверенного корня;
- нет механизма проверки подлинности (любой может выпустить сертификат с любым CN);
- злоумышленник может подменить сертификат на свой и пользователь не отличит.

Чтобы пользователь не прокликивал предупреждение (и не привыкал так делать — это антипаттерн!), мы используем Let's Encrypt — бесплатный доверенный CA.

### 4.6. SNI — Server Name Indication

SNI (RFC 6066) — расширение TLS, позволяющее клиенту в открытом ClientHello передать, к какому домену он хочет подключиться. Это нужно, потому что один IP может хостить много сертификатов (виртуальный хостинг). Без SNI сервер не знает, какой сертификат отдать до того, как получил HTTP Host-заголовок (но HTTP он получит уже внутри TLS).

**Что видит провайдер (ISP) до TLS 1.3 с ESNI/ECH:** SNI идёт в открытом виде. Провайдер видит:
- IP назначения;
- порт назначения;
- SNI (имя домена, к которому подключаемся);
- размеры TLS-пакетов;
- тайминги.

Не видит:
- содержимое HTTP-запросов;
- заголовки HTTP;
- куки.

**Encrypted Client Hello (ECH)** — новое расширение TLS 1.3, шифрует SNI. Пока экспериментальное, поддержка частичная.

**Для чего в нашем проекте важен SNI.** Во-первых, nginx с `server_name <YOUR_DOMAIN>` выбирает нужный server-блок на основе SNI. Во-вторых — и это ключевое — Reality использует SNI для маскировки. В ClientHello от VPN-клиента на порт 443 передаётся `SNI: <MASKED_SNI_HOST>`, и Xray решает:
- если валидация Reality прошла — это наш клиент, дальше VLESS-трафик;
- если валидация не прошла — это посторонний запрос, и Xray прозрачно проксирует handshake и остальной трафик на `<MASKED_SNI_HOST>:443`.

Для ISP это выглядит как обычный HTTPS к `<MASKED_SNI_HOST>`: SNI = <MASKED_SNI_HOST>, сертификат = <MASKED_SNI_HOST>, fingerprint TLS = как у браузера.

### 4.7. Reality — расширение над TLS

Reality — разработанная в экосистеме Xray технология, позволяющая сервису имитировать TLS-поведение произвольного стороннего хоста (arbitrary TLS destination). Суть в следующем.

Стандартная настройка TLS выглядит как «вот мой сертификат, вот мой ключ». Reality устроена иначе — сервер не имеет *собственного* публичного сертификата, вместо этого он хранит приватный ключ Curve25519, а клиент знает парный публичный ключ. Во время ClientHello клиент внутри зашифрованного ClientRandom передаёт короткий идентификатор (shortId), зашифрованный совместно с publicKey сервера. Реализация Reality на сервере:

1. Принимает ClientHello.
2. Пытается расшифровать shortId своим приватным ключом.
3. Если расшифровка успешна и shortId валиден — отвечает как обычный TLS-сервер, но дальше обрабатывает трафик как VLESS.
4. Если расшифровка не удалась — `dest` целевой домен (в нашем случае `<MASKED_SNI_HOST>:443`) берёт на себя весь handshake: Xray открывает TCP к `<MASKED_SNI_HOST>`, пересылает туда ClientHello и дальше работает как прозрачный TCP-прокси.

Вот конфиг Reality в нашем Xray:

```json
// server/xray-server.json — фрагмент
"streamSettings": {
  "network": "tcp",
  "security": "reality",
  "realitySettings": {
    "dest": "<MASKED_SNI_HOST>:443",         ← куда уходит нераспознанный трафик
    "serverNames": ["<MASKED_SNI_HOST>"],     ← SNI, которые сервер «принимает»
    "privateKey": "EK_PPmb...",   ← приватный ключ Curve25519
    "shortIds": ["<SHORT_ID_HEX>"]  ← белый список клиентских идентификаторов
  }
}
```

Ключевое свойство: даже если посторонний отправит запрос к нашему серверу на :443 и попытается проанализировать ответ — он получит ровно тот же TLS, что и настоящий `<MASKED_SNI_HOST>`, включая сертификат `<MASKED_SNI_HOST>` (который вернул `<MASKED_SNI_HOST>` сам, а мы только пересылали байты). С точки зрения ISP, сертификата и fingerprint'а — наш сервер неотличим от внешнего ресурса, под который маскируется.

По сути это — SNI masking + traffic pattern obfuscation: SNI всё тот же `<MASKED_SNI_HOST>`, сертификат — от `<MASKED_SNI_HOST>`, статистические паттерны (размеры TLS-пакетов, тайминги) имитируют реальный трафик.

### 4.8. HSTS, X-Content-Type-Options, остальные security-заголовки

В nginx мы добавляем заголовки безопасности:

```nginx
# deploy/nginx-lockdown.conf:27-30
add_header Strict-Transport-Security "max-age=31536000" always;
add_header X-Content-Type-Options nosniff always;
add_header X-Frame-Options DENY always;
add_header Referrer-Policy strict-origin-when-cross-origin always;
```

**HSTS (HTTP Strict Transport Security, RFC 6797).** `max-age=31536000` (1 год). Браузер, получивший этот заголовок, запомнит на год: «к этому домену ходить только по HTTPS». Даже если пользователь вручную наберёт `http://<YOUR_DOMAIN>`, браузер сам преобразует в HTTPS до отправки запроса. Защита от SSL-stripping-атак (MITM, который переводит HTTPS → HTTP).

**X-Content-Type-Options: nosniff.** Запрещает браузеру «угадывать» MIME-тип файла вопреки `Content-Type`. Защита от MIME-confusion атак (когда злоумышленник загружает JS под видом изображения).

**X-Frame-Options: DENY.** Запрещает встраивание страницы в iframe. Защита от clickjacking.

**Referrer-Policy: strict-origin-when-cross-origin.** При переходе по внешней ссылке передаётся только origin (схема + домен + порт), без пути. Меньше утечек URL-параметров.

### 4.9. Почему в nginx нельзя было оставить self-signed

Теоретически можно, и ACME не обязательна. Но тогда при каждом заходе на админку браузер показывает страшное предупреждение. Для публичного сервиса это — нарушение UX-ожиданий и плохой сигнал про безопасность. Let's Encrypt — бесплатный CA с 90-дневными сертификатами, автоматически продляется через certbot.

## 5. L7 — HTTP/1.1 и HTTP/2

HTTP — базовый прикладной протокол для веб-админки и всех сопутствующих сервисов. В проекте одновременно используются две версии: HTTP/2 наружу (публичный nginx на 4443) и HTTP/1.1 внутри (nginx → FastAPI на 127.0.0.1:8001).

### 5.1. HTTP/1.1: базовые принципы

HTTP/1.1 (RFC 7230-7235) — текстовый stateless-протокол запрос/ответ. Основные свойства:

- **Текстовый формат.** Запросы и заголовки — ASCII-строки, разделённые `\r\n`. Тело может быть бинарным.
- **Stateless.** Каждый запрос независим. Состояние (сессию) приходится эмулировать через куки или JWT.
- **Persistent connections.** В 1.1 по умолчанию соединение не закрывается после каждого запроса (`Connection: keep-alive`). На одном TCP можно сделать несколько запросов подряд.
- **Pipelining.** Можно отправлять несколько запросов, не дожидаясь ответов. На практике не прижилось из-за head-of-line blocking.

**Пример запроса:**

```
GET /api/stats HTTP/1.1
Host: <YOUR_DOMAIN>
Accept: application/json
Authorization: Bearer eyJhbGciOiJIUzI1NiI...
Connection: keep-alive

```

**Пример ответа:**

```
HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: 142
Server: nginx

{"users":[{"name":"alice","uplink":12345,"downlink":67890}]}
```

**Head-of-line blocking в HTTP/1.1.** На одном TCP-коннекте запросы обрабатываются строго по порядку. Если первый запрос «застрял» (сервер долго отвечает), следующие ждут, даже если они лёгкие. Клиенты (браузеры) обходили это открытием 6+ параллельных TCP к одному хосту.

### 5.2. HTTP/2: мультиплексирование и бинарный формат

HTTP/2 (RFC 7540) — бинарный, мультиплексированный транспорт с фреймированием.

**Ключевые изменения:**

1. **Бинарный фреймовый слой.** Вместо текстовых сообщений — бинарные frame'ы: HEADERS, DATA, SETTINGS, PING, GOAWAY, RST_STREAM, WINDOW_UPDATE, PRIORITY.

2. **Мультиплексирование стримов.** В одном TCP-соединении параллельно существуют десятки стримов, каждый — независимый запрос/ответ. Нет head-of-line blocking на уровне HTTP (но остаётся на уровне TCP — потеря TCP-пакета блокирует все стримы).

3. **HPACK (RFC 7541) — сжатие заголовков.** Заголовки сжимаются через статическую + динамическую таблицы + Huffman. Экономия на повторяющихся заголовках (User-Agent, Cookie, Host в одном соединении).

4. **Server push (редко используется).** Сервер может предварительно отправить ресурс, который клиент не запрашивал, но который ему понадобится (например, CSS, связанный с HTML). Часто отключают — сложность и редкий выигрыш.

5. **Flow control.** Управление потоком на уровне стримов и коннекшна — окна WINDOW_UPDATE.

### 5.3. Почему nginx наружу отдаёт HTTP/2, а внутрь идёт HTTP/1.1

Смотрим конфиг:

```nginx
# deploy/nginx-lockdown.conf:16 — слушаем клиентов
listen 4443 ssl http2;

# deploy/nginx-lockdown.conf:35, 48 — ходим к бэкенду
proxy_pass http://127.0.0.1:8001;
proxy_http_version 1.1;
```

**Почему публичный порт HTTP/2.** Современные браузеры умеют HTTP/2 и выигрывают от мультиплексирования — одна страница подтягивает десятки ресурсов (CSS, JS, иконки) через один TCP. HPACK-сжатие заголовков экономит трафик, особенно на Cookie и Authorization.

**Почему внутренний proxy_pass — HTTP/1.1.**

1. **WebSocket требует HTTP/1.1.** Upgrade-механизм (101 Switching Protocols) определён в HTTP/1.1. В HTTP/2 есть `:protocol` pseudo-header для WS-over-HTTP/2 (RFC 8441), но его поддержка в uvicorn и Starlette неполная. Для стабильности используем 1.1.

2. **FastAPI / uvicorn внутри не выиграют от HTTP/2.** Мультиплексирование нужно, когда сотни параллельных запросов делит один TCP. Между nginx и FastAPI на loopback — минимальная задержка, overhead HTTP/2 не окупается. HTTP/1.1 с keep-alive + несколькими worker'ами uvicorn справляется.

3. **Отладка проще.** HTTP/1.1 — текстовый, читается в tcpdump/Wireshark напрямую. HTTP/2 — бинарный, нужен дешифратор.

4. **Nginx по умолчанию не поддерживает HTTP/2 для бэкенда.** Директива `proxy_http_version 1.1` явно указывает версию на бэкенд.

**Ответ от сервера (nginx):**

| Заголовок | Значение |
|---|---|
| `Content-Type` | `text/html; charset=utf-8` |

**Специальные заголовки для прокси:**

```nginx
proxy_set_header Host $host;
proxy_set_header X-Real-IP $remote_addr;
proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
proxy_set_header X-Forwarded-Proto $scheme;
```

- **`Host`** — оригинальный `Host` от клиента, нужен FastAPI для корректной работы с относительными ссылками.
- **`X-Real-IP`** — реальный IP клиента (до проксирования), чтобы приложение видело, не IP nginx.
- **`X-Forwarded-For`** — цепочка IP прокси (стандарт, RFC 7239 определяет альтернативу — `Forwarded`).
- **`X-Forwarded-Proto`** — была ли исходная схема HTTPS. Важно для генерации абсолютных URL в приложении.

Без этих заголовков FastAPI видел бы `Host: 127.0.0.1:8001`, `remote_addr=127.0.0.1` и думал бы, что работает по HTTP.

### 5.7. CORS и preflight

CORS (Cross-Origin Resource Sharing) — механизм, позволяющий контролировать, с каких внешних origin'ов браузер может делать запросы к API. Без CORS браузер по Same-Origin Policy запрещает JS запрашивать ресурсы с другого origin.

Origin = `схема + домен + порт`. Например, `https://<YOUR_DOMAIN>:4443`.

**Preflight OPTIONS.** Перед нестандартным запросом (не-GET/POST, или с custom-заголовками) браузер отправляет OPTIONS:

```
OPTIONS /api/keys HTTP/1.1
Host: <YOUR_DOMAIN>
Origin: https://example.com
Access-Control-Request-Method: POST
Access-Control-Request-Headers: Authorization, Content-Type
```

Сервер отвечает:

```
HTTP/1.1 204 No Content
Access-Control-Allow-Origin: https://example.com
Access-Control-Allow-Methods: GET, POST, DELETE
Access-Control-Allow-Headers: Authorization, Content-Type
Access-Control-Max-Age: 3600
```

Если сервер не разрешает — браузер блокирует реальный запрос, даже не отправив его.

В нашем проекте админка работает на одном origin (`<YOUR_DOMAIN>:4443`) и внешние origin'ы не нужны. CORS-заголовки настраиваются в FastAPI через `CORSMiddleware`, если потребуется открыть API.

### 5.8. HTTP/3 — почему не у нас

HTTP/3 (RFC 9114) работает поверх QUIC (RFC 9000) — UDP-транспорт с встроенным TLS 1.3. Преимущества:
- 0-RTT подключение к известному серверу;
- нет head-of-line blocking на транспортном уровне (каждый стрим со своим порядком);
- быстрая реакция на потерю пакетов;
- миграция соединения (смена IP без reconnect).

**Почему у нас HTTP/2, а не HTTP/3.** Во-первых, HTTP/3 — UDP, а у нас везде TCP (см. выше, причины). Во-вторых, nginx mainline только недавно (с версии 1.25) получил экспериментальную поддержку HTTP/3, продакшен-ready она не у всех. В-третьих, выгода для нашей небольшой админки минимальна. Для крупных CDN — другое дело.

## 6. L7 — WebSocket (RFC 6455)

WebSocket — прикладной протокол, предоставляющий двунаправленный full-duplex канал поверх TCP после HTTP-апгрейда. В проекте он используется для push-а статистики из бэкенда в браузер админа (`web/routes_ws.py`, эндпоинт `/ws/stats`).

### 6.1. Handshake: HTTP Upgrade → WebSocket

WebSocket начинается как обычный HTTP/1.1 GET, но со специальными заголовками. Сервер, поняв, что это ws-рукопожатие, переключает протокол.

**Запрос клиента:**

```
GET /ws/stats?token=eyJhbGc... HTTP/1.1
Host: <YOUR_DOMAIN>:4443
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
Sec-WebSocket-Version: 13
Sec-WebSocket-Protocol: stats.v1     ← опционально, сабпротокол
Origin: https://<YOUR_DOMAIN>:4443
```

**Ответ сервера:**

```
HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=
Sec-WebSocket-Protocol: stats.v1
```

**Как вычисляется `Sec-WebSocket-Accept`:**

```
magic = "258EAFA5-E914-47DA-95CA-C5AB0DC85B11"
concat = Sec-WebSocket-Key + magic
digest = SHA1(concat)           ← 20 байт
accept = base64(digest)          ← ~28 символов
```

Это доказательство серверу, что он действительно понимает протокол WebSocket, а не просто отвечает 101 без понимания. Клиент проверяет — если accept не совпадает, считает handshake невалидным.

После 101 Switching Protocols TCP-коннекшн перестаёт быть HTTP — по нему идут WebSocket-frames.

### 6.2. Проброс через nginx

В nginx нужно явно включить upgrade-механизм:

```nginx
# deploy/nginx-lockdown.conf:34-45
location /ws/ {
    proxy_pass http://127.0.0.1:8001;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_read_timeout 3600s;
    proxy_send_timeout 3600s;
}
```

**Что именно делают эти строки:**

- `proxy_http_version 1.1` — обязательно, иначе nginx попытается проксировать по HTTP/1.0, в котором нет Upgrade.
- `proxy_set_header Upgrade $http_upgrade` — пробрасывает клиентский `Upgrade: websocket` на бэкенд. Без этого FastAPI не поймёт, что пришёл WS-запрос.
- `proxy_set_header Connection "upgrade"` — заменяет заголовок на явный `"upgrade"`. Nginx по умолчанию прячет hop-by-hop-заголовки (Connection в их числе), и без этой строки Connection вообще не доходит до бэкенда.
- `proxy_read_timeout 3600s` / `proxy_send_timeout 3600s` — длинный таймаут, чтобы простаивающий WebSocket не закрывался.

Без любой из этих строк — HTTP-ответ 101 не доходит или доходит без Connection: upgrade, и клиент считает handshake сломанным.

### 6.3. Структура WebSocket-фрейма

После handshake поток байт состоит из frames. Один frame:

```
 0               1               2               3
 0 1 2 3 4 5 6 7 0 1 2 3 4 5 6 7 0 1 2 3 4 5 6 7 0 1 2 3 4 5 6 7
+-+-+-+-+-------+-+-------------+-------------------------------+
|F|R|R|R| opcode|M| Payload len |   Extended payload length     |
|I|S|S|S| (4)   |A|   (7)       |   (16 / 64 bits)              |
|N|V|V|V|       |S|             |                               |
| |1|2|3|       |K|             |                               |
+-+-+-+-+-------+-+-------------+-------------------------------+
|   Masking-key (если MASK=1, 4 байта)                          |
+---------------------------------------------------------------+
|                     Payload Data                              |
|                     ...                                       |
+---------------------------------------------------------------+
```

**Поля:**

- **FIN (1 бит)** — флаг, что это последний фрагмент сообщения (сообщение может быть разбито на несколько frames).
- **RSV1-3 (3 бита)** — зарезервированы, 0 если нет расширений.
- **opcode (4 бита)** — тип фрейма.
- **MASK (1 бит)** — шифрование payload XOR-маской (всегда 1 от клиента, всегда 0 от сервера).
- **Payload len (7 бит + extended)** — длина payload:
  - 0-125: значение = длина;
  - 126: следующие 2 байта — длина (uint16);
  - 127: следующие 8 байт — длина (uint64).
- **Masking-key (4 байта)** — случайный ключ, которым XOR-ится payload от клиента.
- **Payload Data** — тело фрейма.

**Opcodes:**

| Opcode | Значение |
|---|---|
| 0x0 | Continuation frame (продолжение предыдущего) |
| 0x1 | Text frame (UTF-8) |
| 0x2 | Binary frame |
| 0x8 | Close |
| 0x9 | Ping |
| 0xA | Pong |

### 6.4. Text vs Binary frames

- **Text frame (0x1)** — payload — валидный UTF-8 текст. В нашем проекте это JSON-сообщения (`{"type": "snapshot", ...}`).
- **Binary frame (0x2)** — payload — произвольные байты. Используется, когда надо передать бинарные данные (Protobuf, файлы).

В `web/routes_ws.py` мы используем `ws.send_text(json.dumps(...))` — значит, text frame.

### 6.5. Ping/Pong — уровни

Есть два уровня ping/pong, которые часто путают:

**Ping-frame/Pong-frame (opcodes 0x9/0xA)** — это *протокольные* фреймы WebSocket (RFC 6455, section 5.5.2-5.5.3). Любая сторона может отправить Ping, получатель *обязан* ответить Pong с тем же payload. Назначение — keep-alive, проверка живости, heartbeat.

**JSON-уровень ping/pong** — в нашем коде:

```python
# web/routes_ws.py
async def _heartbeat_loop(ws: WebSocket) -> None:
    while True:
        await asyncio.sleep(HEARTBEAT_INTERVAL_SEC)
        await ws.send_text(json.dumps({"type": "ping", "ts": time.time()}))

async def _reader_loop(ws: WebSocket) -> None:
    while True:
        raw = await ws.receive_text()
        try:
            msg = json.loads(raw)
        except json.JSONDecodeError:
            continue
        if msg.get("type") == "pong":
            continue
```

Мы шлём `{"type": "ping"}` как text-frame, клиент отвечает `{"type": "pong"}` — тоже text-frame. Это *прикладной* heartbeat поверх текстового канала.

**Почему не использовать protocol-level ping?** В принципе можно, но есть нюансы:
- некоторые WS-библиотеки не дают удобного API для отправки Ping-фреймов и отслеживания Pong'ов;
- в Starlette/FastAPI работа с ping/pong низкого уровня требует спуститься к `websocket.send({"type": "websocket.ping"})`, что нетривиально;
- JSON-ping вписывается в общий формат сообщений на канале и хорошо логируется.

Это сознательный выбор — **управлять живостью соединения на прикладном уровне**, проще для отладки и для демонстрации на защите: в логах видна каждая ping-проба как отдельное JSON-сообщение.

### 6.6. Close frame, status codes

При завершении соединения любая сторона посылает Close-frame (opcode 0x8) с 2-байтным status code и опциональным UTF-8 reason. Получатель отвечает своим Close и закрывает TCP.

Коды из RFC 6455:

| Код | Название | Когда |
|---|---|---|
| 1000 | Normal Closure | штатное завершение |
| 1001 | Going Away | сервер выключается, страница закрывается |
| 1002 | Protocol Error | нарушение WS-протокола |
| 1003 | Unsupported Data | получен binary, когда ожидался text |
| 1005 | No Status Rcvd | статус не указан (reserved, только для API) |
| 1006 | Abnormal Closure | TCP оборвался без Close (reserved, только для API) |
| 1007 | Invalid Frame Payload | невалидный UTF-8 в text-frame |
| 1008 | Policy Violation | клиент нарушил политику сервера |
| 1009 | Message Too Big | превышен лимит размера |
| 1010 | Mandatory Ext | клиент требует расширение, которого нет |
| 1011 | Internal Error | сервер упал с ошибкой |
| 1012 | Service Restart | сервер перезапускается |
| 1013 | Try Again Later | временная недоступность |
| 1014 | Bad Gateway | прокси получил плохой ответ от upstream |
| 1015 | TLS Handshake | не удалось TLS (reserved, только для API) |

В нашем коде явно используется 1008:

```python
# web/routes_ws.py:26
await ws.close(code=status.WS_1008_POLICY_VIOLATION)
```

Это происходит, когда JWT-токен из query-параметра не прошёл валидацию — клиент не имеет права на подключение.

### 6.7. Почему WebSocket, а не SSE / long-polling / WebTransport

Альтернативы для real-time push:

| Технология | Направление | Транспорт | Плюсы | Минусы | Пригодилось бы? |
|---|---|---|---|---|---|
| WebSocket | full-duplex | TCP+HTTP upgrade | двусторонний, минимум overhead, бинарь | сложнее nginx-конфиг, handshake | да, у нас |
| SSE | server→client | обычный HTTP response с `text/event-stream` | простота, встроен в браузер | только сервер→клиент, только текст | подошло бы, но мы хотим от клиента пинги |
| Long-polling | эмуляция | HTTP GET, сервер долго держит | совместимость со старыми прокси | неэффективно, плодит коннекты | нет |
| gRPC-Web stream | bidi | HTTP/2 | типобезопасность, Protobuf | тяжёлый клиент, браузеру нужна прослойка | нет, overkill |
| WebTransport | bidi | HTTP/3 (QUIC) | современный, без HOL | сырая поддержка, UDP | нет, рано |

Мы выбрали WebSocket, потому что:
1. Нужен двусторонний канал (от клиента тоже могут приходить pong-ы и потенциально команды).
2. Он поддерживается везде — все современные браузеры.
3. FastAPI/Starlette даёт удобный async API.
4. nginx умеет проксировать WS без дополнительных модулей.

### 6.8. Код WebSocket-обработчика

Посмотрим внимательно на `web/routes_ws.py`:

```python
@router.websocket("/ws/stats")
async def ws_stats(
    ws: WebSocket,
    token: str | None = Query(default=None),
    settings: Settings = Depends(get_settings),
) -> None:
    try:
        authorize_ws_token(token, settings)        # 1. проверка JWT
    except Exception:
        await ws.close(code=status.WS_1008_POLICY_VIOLATION)
        return

    await ws.accept()                              # 2. приём коннекта (отправка 101)
    poller = ws.app.state.poller
    queue = poller.subscribe()                     # 3. подписка на поток апдейтов

    sender = asyncio.create_task(_sender_loop(ws, queue), name="ws-sender")
    heartbeat = asyncio.create_task(_heartbeat_loop(ws), name="ws-heartbeat")
    reader = asyncio.create_task(_reader_loop(ws), name="ws-reader")

    done, pending = await asyncio.wait(
        [sender, heartbeat, reader],
        return_when=asyncio.FIRST_COMPLETED,       # 4. если любой из тасков завершился — выходим
    )
    for task in pending:
        task.cancel()
    poller.unsubscribe(queue)
    ...
```

**Важные архитектурные решения:**

1. **JWT в query-параметре**, а не в заголовке, потому что браузерный WebSocket API (`new WebSocket(url)`) не даёт задать custom headers. Токен кладётся в URL `wss://.../ws/stats?token=xxx`.
2. **Три independent-таска** — sender, heartbeat, reader. `asyncio.wait` ждёт, пока *любой* из них завершится. Если обрывается соединение — reader/sender бросает `WebSocketDisconnect`, и мы корректно выходим.
3. **Queue-subscribe pattern** — подписка на общий poller (отдельный фоновый процесс, который опрашивает Xray statsquery и publish'ит снэпшоты). Все подключённые админы получают свои копии в своих очередях.
4. **Heartbeat каждые 30 секунд** — предотвращает разрыв NAT-state и nginx-timeout, плюс даёт клиенту возможность определить, что сервер живой.

## 7. L7 — gRPC (Xray StatsService)

gRPC — RPC-фреймворк, разработанный Google, работающий поверх HTTP/2 с сериализацией Protocol Buffers. В проекте он задействован только в одном месте — внутренний API статистики Xray.

### 7.1. Что такое gRPC

Аббревиатура RPC — Remote Procedure Call. Идея: вместо REST-запросов «опиши ресурс, отправь HTTP-запрос, парси JSON» — ты вызываешь метод как функцию, а библиотека под капотом делает сеть и сериализацию.

**Стек:**

```
┌─────────────────────────────┐
│ Ваш код — client.Foo(req)   │ ← типизированный Protobuf-объект
├─────────────────────────────┤
│ gRPC-stub (сгенерированный) │
├─────────────────────────────┤
│ Protocol Buffers — бинарный │ ← сериализация
├─────────────────────────────┤
│ HTTP/2 frames (DATA, HEADERS)│ ← транспорт, streaming, сжатие
├─────────────────────────────┤
│ TLS (опционально)           │
├─────────────────────────────┤
│ TCP                         │
└─────────────────────────────┘
```

**Свойства gRPC:**

- **Бинарь.** Protobuf в разы компактнее JSON, парсится быстрее.
- **Типобезопасность.** .proto-файл описывает сообщения, генератор делает классы для Go/Python/JS.
- **Streaming.** Четыре типа методов: unary (req → resp), server-streaming (req → stream resp), client-streaming (stream req → resp), bidi (stream ↔ stream).
- **Встроенный keep-alive, cancellation, deadlines.**

### 7.2. Где в проекте

Xray слушает gRPC StatsService на `127.0.0.1:10085` (loopback only):

```json
// server/xray-server.json
{
  "api": {
    "tag": "api",
    "services": ["StatsService"]
  },
  "inbounds": [
    {
      "tag": "api-in",
      "listen": "127.0.0.1",      ← ТОЛЬКО LOOPBACK
      "port": 10085,
      "protocol": "dokodemo-door", ← внутренний прокси на API
      "settings": { "address": "127.0.0.1" }
    },
    ...
  ],
  "routing": {
    "rules": [
      { "inboundTag": ["api-in"], "outboundTag": "api", "type": "field" }
    ]
  }
}
```

**Почему loopback.** Статистика трафика пользователей — чувствительные данные. Если gRPC-API слушал на `0.0.0.0:10085`, любой из Интернета мог бы сделать `xray api statsquery --server=<YOUR_VPS_IP>:10085` и получить список email'ов и байт. Плюс, в gRPC-API Xray нет встроенной аутентификации (нет TLS-клиент-сертификата или токена) — так что защита исключительно сетевая.

### 7.3. Как мы обращаемся к gRPC — через subprocess

Архитектурное решение: **FastAPI НЕ говорит gRPC напрямую**. Вместо этого мы запускаем `xray api statsquery --server=127.0.0.1:10085` как subprocess и парсим его JSON-вывод.

```python
# гипотетический код в web/poller.py / bot/stats.py
proc = await asyncio.create_subprocess_exec(
    "xray", "api", "statsquery", "--server=127.0.0.1:10085",
    stdout=asyncio.subprocess.PIPE,
)
stdout, _ = await proc.communicate()
data = json.loads(stdout)
# data = {"stat": [{"name": "user>>>alice>>>traffic>>>uplink", "value": 12345}, ...]}
```

**Обоснование такого выбора:**

1. **Не нужно тянуть `grpcio` и `protobuf`** — это большие зависимости (~20 МБ), а у нас VPS с 1.8 GB RAM.
2. **Не нужно копировать .proto-файлы Xray** и генерировать Python-стабы. Это хрупко (обновление Xray ломает стабы).
3. **Изоляция.** Xray CLI уже умеет парсить ответ и выдавать готовый JSON. Мы только проксируем.
4. **Простота отладки.** Можно из консоли руками запустить `xray api statsquery` и увидеть ровно то, что видит наш бэкенд.

**Минус:** на каждый вызов запускается процесс (~10-30 мс форк+exec+gRPC-handshake). Для редкого опроса (раз в 2-5 секунд) это терпимо.

### 7.4. Альтернатива — прямой gRPC из Python

Можно было бы:

```python
import grpc
import xray.app.stats.command.command_pb2 as stats_pb
import xray.app.stats.command.command_pb2_grpc as stats_rpc

channel = grpc.aio.insecure_channel("127.0.0.1:10085")
stub = stats_rpc.StatsServiceStub(channel)
response = await stub.QueryStats(stats_pb.QueryStatsRequest(pattern=""))
```

Плюсы: быстрее (нет форка), потоковые ответы, стабильная типизация. Минусы: зависимости, хрупкость к версии Xray, overhead для малой нагрузки. Для нашего кейса оптимальнее subprocess.

### 7.5. HTTP/2-особенности gRPC

gRPC — один из главных пользователей HTTP/2-мультиплексирования. Один долгоживущий TCP с десятками одновременных стримов, каждый — отдельный RPC. Заголовки сжимаются через HPACK. Streaming-методы — просто стрим DATA-фреймов.

Плата за это — HTTP/2 head-of-line blocking: потеря TCP-пакета останавливает *все* стримы этого TCP. В gRPC-over-QUIC (HTTP/3) эту проблему решают.

## 8. L7 — JWT (RFC 7519)

JWT (JSON Web Token) — компактный формат передачи подписанных JSON-утверждений между сторонами. В проекте мы используем JWT для аутентификации WebSocket-соединения.

### 8.1. Структура

JWT состоит из трёх частей, разделённых точкой:

```
<base64url(header)>.<base64url(payload)>.<base64url(signature)>
```

**Пример:**

```
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9
.
eyJzdWIiOiIxMjM0NTY3ODkwIiwibmFtZSI6IkpvaG4iLCJpYXQiOjE1MTYyMzkwMjJ9
.
SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c
```

**Header (декодированный):**

```json
{
  "alg": "HS256",
  "typ": "JWT"
}
```

- `alg` — алгоритм подписи (HS256, RS256, ES256, none).
- `typ` — тип токена (всегда "JWT").

**Payload (claims):**

```json
{
  "sub": "admin_user_1",      ← subject — идентификатор субъекта
  "exp": 1713520000,          ← expiration time (Unix)
  "iat": 1713516400,          ← issued at
  "iss": "lockdown-web",      ← issuer
  "role": "admin"             ← custom-claim
}
```

Стандартные claims из RFC 7519:
- `iss` (issuer) — кто выпустил;
- `sub` (subject) — кто субъект;
- `aud` (audience) — кому предназначен;
- `exp` (expiration) — когда истекает;
- `nbf` (not before) — с какого момента валиден;
- `iat` (issued at) — когда выпущен;
- `jti` (JWT ID) — уникальный идентификатор токена.

**Signature (HS256):**

```
signature = HMAC-SHA256(
    key   = SECRET_KEY,
    data  = base64url(header) + "." + base64url(payload)
)
```

### 8.2. HS256 vs RS256

**HS256 (HMAC-SHA256) — симметричный.** Один и тот же секрет и для подписи, и для проверки. Быстрее, короче токен. Годится, когда один и тот же сервис и выпускает, и проверяет токен — как у нас.

**RS256 (RSA-SHA256) — асимметричный.** Приватный ключ подписывает, публичный проверяет. Нужен, когда выпускающий и проверяющий — разные сервисы (например, OAuth IdP и сотни consumer-приложений).

Мы выбрали HS256, потому что:
1. Один FastAPI-процесс и выпускает, и проверяет.
2. Секрет из `settings.SECRET_KEY` хранится в одном месте (`.env`).
3. Не нужна инфраструктура ключей.

### 8.3. Как сервер проверяет

Алгоритм проверки:

```python
def verify_jwt(token: str, secret: str) -> dict:
    header_b64, payload_b64, signature_b64 = token.split(".")
    
    # 1. декодировать header, проверить alg
    header = json.loads(base64url_decode(header_b64))
    if header["alg"] != "HS256":
        raise ValueError("algorithm mismatch")
    
    # 2. вычислить ожидаемую подпись
    expected = HMAC_SHA256(secret, f"{header_b64}.{payload_b64}")
    
    # 3. сравнить в constant-time
    if not hmac.compare_digest(expected, base64url_decode(signature_b64)):
        raise ValueError("invalid signature")
    
    # 4. декодировать payload, проверить exp/nbf/iat
    payload = json.loads(base64url_decode(payload_b64))
    if payload.get("exp", float("inf")) < time.time():
        raise ValueError("expired")
    
    return payload
```

**Constant-time сравнение** (`hmac.compare_digest`) важно, чтобы не давать timing-oracle. Обычный `==` у строк short-circuit'ится на первом различии, и по времени ответа можно восстановить подпись по байтам. `compare_digest` всегда сравнивает всю длину.

В коде `web/routes_ws.py:24` вызов `authorize_ws_token(token, settings)` делает всё это. Если валидация упала — 1008 Policy Violation.

### 8.4. Уязвимости JWT и как мы с ними живём

**1. Алгоритм `none`.** Если декодировать header, подставить `"alg": "none"` и убрать signature — некоторые *сломанные* реализации примут. В `PyJWT` (и в нашем коде) явно передаётся список разрешённых алгоритмов: `jwt.decode(token, secret, algorithms=["HS256"])`. Без этой защиты — уязвимость.

**2. Алгоритм RS256 → HS256 confusion.** Если сервер принимает любой `alg`, а ключ — публичный RSA (который «известен»), атакующий меняет `alg` на HS256 и подписывает токен публичным ключом. Сервер проверяет HMAC с публичным ключом → всё сходится. Защита — тот же whitelist алгоритмов.

**3. Перебор секрета.** Если `SECRET_KEY` слабый (короткий, словарный), злоумышленник может офлайн подобрать по известному JWT. Защита: длинный случайный секрет (32+ байт, `os.urandom(32)`).

**4. Отсутствие revocation.** JWT — stateless. Если админ скомпрометирован, токен до `exp` продолжает работать. Решения:
- короткий `exp` (минуты) + refresh-токены;
- blacklist скомпрометированных `jti` в Redis (ломает stateless);
- ротация секрета (ломает все выпущенные токены).

У нас токены с `exp` на час — компромисс между удобством и рисками.

**5. Хранение на клиенте.** Если токен в `localStorage`, любой XSS читает его. Если в `HttpOnly` cookie — защищён от XSS, но нужен CSRF. Мы передаём токен в query-параметре `?token=...` — тоже компромисс (попадает в server-логи), но браузерный WS API не оставляет вариантов.

**6. Размер.** Большой payload = большой токен. Всё улетает в каждом запросе (или в URL). Стараемся класть только `sub` и `exp`.

## 9. L7 — Telegram Bot API

Telegram Bot API — это HTTPS-обёртка над внутренним протоколом Telegram MTProto. Бот не говорит MTProto напрямую, вместо этого ходит к `api.telegram.org:443` по HTTPS с JSON-телами.

### 9.1. Почему бот не требует публичного IP

Ключевое свойство: **бот всегда инициирует соединение сам**. Он говорит Telegram: «дай мне обновления». Telegram не открывает соединение к боту. Поэтому бот может жить:
- за NAT дома;
- на корпоративном сервере без public IP;
- на нашем VPS — неважно.

Это отличает long-polling от webhook-подхода.

### 9.2. Long-polling: принцип работы

Бот отправляет:

```
POST https://api.telegram.org/bot<TOKEN>/getUpdates HTTP/1.1
Host: api.telegram.org
Content-Type: application/json

{"offset": 12345, "timeout": 60}
```

Telegram-сервер:
- если есть апдейт с offset >= 12345 — сразу возвращает;
- если нет — **держит ответ открытым** до 60 секунд, ожидая нового сообщения;
- если за 60 секунд ничего нет — возвращает пустой массив.

```
Telegram server                                   Bot
     │                                             │
     │ ◄──── POST /getUpdates timeout=60 ─────── │
     │                                             │
     │   [ждёт 60 сек или пока не придёт апдейт]   │
     │                                             │
     │ ───── 200 OK [{upd1}, {upd2}] ───────────►│
     │                                             │
     │                                             │
     │ ◄──── POST /getUpdates timeout=60 ─────── │ offset = upd2.id + 1
     │                                             │
```

**Эффект:**
- минимум лишних запросов (один в минуту в простое);
- минимальная задержка прихода апдейта (мгновенно, как только Telegram получает сообщение пользователя);
- TCP-коннекшн keep-alive + HTTP/2 — обычно один коннект живёт весь день.

### 9.3. Long-polling vs webhook

**Webhook** — наоборот: бот регистрирует public HTTPS-URL, Telegram *сам* посылает POST на этот URL при каждом апдейте.

| Критерий | Long-polling | Webhook |
|---|---|---|
| Публичный IP | не нужен | нужен |
| Порт открыт снаружи | не нужен | нужен :443 / :80 / :88 / :8443 |
| TLS-сертификат | нужен только клиентский (в `requests`) | нужен *серверный*, валидный |
| Задержка | ~секунда (пока POST завершится) | мгновенно |
| Сложность реализации | проще (один цикл) | нужно держать HTTP-сервер |
| Нагрузка на сервер | постоянная (висит запрос) | только при апдейтах |
| Для редких апдейтов | подходит | подходит |
| Для burst-трафика | может отставать | лучше |

Мы выбрали long-polling, потому что:
1. Не нужно открывать ещё один публичный порт (у нас уже занят 4443 админкой, плюс VPN-порты).
2. Не нужно париться с сертификатом для бота.
3. На 10 активных пользователей нагрузка минимальная.

### 9.4. Основные методы API

| Метод | Назначение |
|---|---|
| `getUpdates` | long-polling апдейтов |
| `sendMessage` | отправить текст |
| `editMessageText` | отредактировать отправленное сообщение |
| `deleteMessage` | удалить |
| `answerCallbackQuery` | ответить на нажатие inline-кнопки |
| `getFile` | скачать файл |
| `getChatMember` | проверить права в чате |
| `setMyCommands` | установить список `/command` в меню |

### 9.5. callback_query и inline-клавиатура

Когда админ нажимает кнопку «Accept» в сообщении бота, Telegram шлёт ему callback_query:

```json
{
  "update_id": 123456,
  "callback_query": {
    "id": "abc123",
    "from": {"id": 987654321, "username": "admin"},
    "message": { ... },
    "data": "acc:<ADMIN_TG_ID>",
    "chat_instance": "..."
  }
}
```

Поле `data` — произвольная строка до 64 байт, которую бот кладёт в кнопку при её создании:

```python
InlineKeyboardButton(text="Accept", callback_data="acc:<ADMIN_TG_ID>")
```

Бот декодирует `data`, делает действие, отвечает:

```
POST /bot<TOKEN>/answerCallbackQuery
{"callback_query_id": "abc123", "text": "Одобрено"}
```

Это важно — Telegram ждёт ответ в течение 30 секунд, иначе кнопка на клиенте зависает в состоянии "загрузка".

### 9.6. Rate limits

Telegram ограничивает:
- 30 сообщений в секунду на разных пользователей;
- 1 сообщение в секунду в один чат;
- 20 сообщений в минуту в группу.

При превышении — 429 Too Many Requests с заголовком `Retry-After`. В нашем боте нагрузка небольшая, пока не упирались.

## 10. L7 — ACME / Let's Encrypt

ACME (Automated Certificate Management Environment, RFC 8555) — протокол для автоматического выпуска X.509-сертификатов. Let's Encrypt — крупнейший ACME-CA, бесплатный, 90-дневные сертификаты, до 50 сертификатов в неделю на registered domain.

### 10.1. HTTP-01 challenge

Самый распространённый способ подтвердить владение доменом — HTTP-01.

**Процедура:**

```
certbot                              Let's Encrypt CA
  │                                         │
  │── POST /newOrder                        │
  │   {identifiers: [{type:"dns",           │
  │                   value:"<YOUR_DOMAIN>"}]}
  │                                    ──► │
  │                                         │
  │◄── orderId, challenge URLs              │
  │                                         │
  │── POST /authz/...                       │
  │                                    ──► │
  │◄── {challenges: [                       │
  │      {type:"http-01", token:"abc123"},  │
  │      {type:"dns-01", ...}               │
  │    ]}                                   │
  │                                         │
  │ кладёт файл                             │
  │ /var/www/certbot/.well-known/           │
  │   acme-challenge/abc123                 │
  │ с содержимым "abc123.<account_thumbprint>"
  │                                         │
  │── POST /challenge/... (ready)           │
  │                                    ──► │
  │                                         │
  │                                   ◄─── │ CA делает GET:
  │                                         │  http://<YOUR_DOMAIN>/
  │                                         │    .well-known/acme-challenge/abc123
  │                                   ───► │
  │                                         │ проверяет содержимое
  │                                         │
  │── polling /order/... status             │
  │                                    ──► │
  │◄── status: valid                        │
  │                                         │
  │── POST /order/.../finalize  (CSR)       │
  │                                    ──► │
  │◄── certificate URL                      │
  │                                         │
  │── GET /cert/...                         │
  │                                    ──► │
  │◄── PEM chain                            │
  │                                         │
  │ сохраняет в                             │
  │ /etc/letsencrypt/live/.../fullchain.pem │
```

**В нашем nginx для этого открыт 80:**

```nginx
# deploy/nginx-lockdown.conf:1-13
server {
    listen 80;
    listen [::]:80;
    server_name <YOUR_DOMAIN>;

    location /.well-known/acme-challenge/ {
        root /var/www/certbot;                ← сюда certbot кладёт токены
    }

    location / {
        return 301 https://$host:4443$request_uri;  ← весь остальной HTTP → HTTPS
    }
}
```

**Почему нужен открытый :80.** Let's Encrypt CA жёстко проверяет HTTP-01 *через порт 80* — никаких редиректов на другие порты. Это защита от тех, кто может перехватить только нестандартный порт. Если :80 закрыт — HTTP-01 не работает. Тогда нужно DNS-01.

### 10.2. DNS-01 challenge — альтернатива

Вместо выкладывания файла на :80, certbot кладёт TXT-запись в DNS:

```
_acme-challenge.<YOUR_DOMAIN>.  TXT  "abc123..."
```

CA делает DNS-запрос и проверяет.

**Плюсы DNS-01:**
- не нужен открытый :80;
- можно выпускать wildcard-сертификаты (`*.<YOUR_DOMAIN>`);
- работает даже если сервер вообще не доступен снаружи (только бэкенд).

**Минусы:**
- нужен API провайдера DNS для автоматизации;
- задержка на распространение DNS-записи.

У нас `fvds.ru` — не даёт удобного API для автоматизации TXT-записей. Поэтому используем HTTP-01.

### 10.3. Rate limits Let's Encrypt

- **50 сертификатов в неделю на registered domain** (eTLD+1). Для `fvds.ru` это значит, что *все* поддомены вида `*.fvds.ru` суммарно могут получить до 50/неделю. Поскольку `fvds.ru` — это общий хостинг-домен, многие клиенты параллельно выпускают сертификаты на свои поддомены, и мы потенциально можем упереться в лимит.
- 5 дубликатов одного сертификата в неделю.
- 300 новых ордеров в 3 часа на аккаунт.
- 5 неудачных валидаций в час.

**Способы обойти лимит:**
1. **Использовать свой домен.** Купить `my-cool-vpn.net` — там своя квота.
2. **Перейти на ZeroSSL.** Альтернативный ACME-CA с похожими лимитами.
3. **Buy-паком коммерческий сертификат.** Одноразовая оплата, ~$10/год.
4. **Self-signed + HPKP.** Антипаттерн, браузер ругается.

У нас — живём с общим fvds.ru, пока не упираемся.

### 10.4. Автопродление

Certbot ставит в cron запуск `certbot renew` раз в день. Внутри проверяет все сертификаты — если до `NotAfter` меньше 30 дней, перевыпускает. После обновления делает `systemctl reload nginx`.

## 11. Сравнительная таблица альтернатив

### 11.1. Push-технологии: WebSocket vs SSE vs Long-polling vs gRPC stream vs WebTransport

| Критерий | WebSocket | SSE | Long-polling | gRPC stream | WebTransport |
|---|---|---|---|---|---|
| Направление | full-duplex | server→client | эмуляция | bidi | bidi |

## 12. Типичные вопросы преподавателя по сети и развёрнутые ответы

Ниже — список вопросов, типичных для защиты курсовой по сетевым технологиям. На каждый — подробный ответ.

### Вопрос 1. Что происходит когда ты нажимаешь F5 в браузере на `https://<YOUR_DOMAIN>:4443`?

Полный цикл, по слоям:

1. **Проверка кэша браузера.** Если ресурс был закэширован с `Cache-Control: max-age=...`, и TTL не истёк, браузер возвращает его из кэша, не обращаясь к сети. F5 обычно делает conditional request (с `If-Modified-Since`). Shift+F5 — bypass cache.
2. **DNS resolution.** Браузер берёт `<YOUR_DOMAIN>` и спрашивает системный резолвер. Если есть в DNS-кэше браузера/ОС — возврат сразу. Иначе идёт рекурсивный DNS-запрос: местный резолвер (провайдера / 1.1.1.1 / 8.8.8.8) → корневой NS → .ru TLD NS → fvds.ru authoritative NS → получаем A-запись `<YOUR_VPS_IP>`.
3. **TCP handshake.** Браузер открывает сокет на `<YOUR_VPS_IP>:4443`. Отправляет SYN, получает SYN-ACK от nginx, отвечает ACK. Соединение в ESTABLISHED.
4. **TLS 1.3 handshake.** ClientHello с SNI=<YOUR_DOMAIN>, key_share X25519, cipher_suites. ServerHello с выбранными параметрами. Certificate — цепочка Let's Encrypt R3 → leaf. CertificateVerify — подпись приватным ключом сервера. Finished — HMAC handshake'а. Клиент проверяет цепочку: root ISRG X1 найден в OS trust-store, подписи валидны, SNI совпадает с SAN сертификата, даты валидны. Клиент отправляет свой Finished.
5. **ALPN-negotiation.** В рамках TLS клиент предлагает `["h2", "http/1.1"]`, сервер выбирает `h2`. Переходим на HTTP/2.
6. **HTTP/2 SETTINGS frame.** Обмен настройками (max concurrent streams, initial window size).
7. **HEADERS frame — GET / HTTP/2.** Заголовки сжимаются HPACK.
8. **Nginx получает запрос,** смотрит `server_name <YOUR_DOMAIN>` → выбирает блок, `location /` → `proxy_pass http://127.0.0.1:8001`. Делает TCP (+ если keep-alive пула нет) на 127.0.0.1:8001, HTTP/1.1 GET с пробросом `X-Forwarded-For`, `Host`, и т.д.
9. **FastAPI/uvicorn обрабатывает,** возвращает HTML + JSON + CSS.
10. **Nginx пакует обратно в HTTP/2,** шифрует TLS, отправляет клиенту.
11. **Браузер получает HTML,** начинает парсить. Для каждого `<link>`, `<script>`, `<img>` открывает новые HTTP/2 streams в том же TCP (благодаря мультиплексированию) или переиспользует существующие.
12. **JavaScript запускается,** может открыть `new WebSocket("wss://.../ws/stats?token=...")` — это ещё один TCP+TLS+HTTP upgrade.
13. **Отрисовка страницы.** Всё, F5 выполнен.

### Вопрос 2. Что такое TLS handshake?

TLS handshake — процедура согласования параметров шифрования между клиентом и сервером, после которой они имеют общий сессионный ключ и могут шифровать прикладной трафик.

**Цели handshake:**
1. Согласовать версию TLS и cipher suite.
2. Обменяться данными для вывода сессионного ключа (обычно эфемерный DH).
3. Аутентифицировать сервер (через сертификат и подпись).
4. Опционально — аутентифицировать клиента (mTLS).
5. Защитить сам handshake от подмены (Finished HMAC).

**В TLS 1.3 handshake занимает 1 RTT** (в TLS 1.2 — 2 RTT). Клиент отправляет ClientHello с key_share, сервер одним flight'ом — ServerHello, EncryptedExtensions, Certificate, CertificateVerify, Finished. Клиент проверяет и отправляет свой Finished + Application Data.

Ключевые расширения: SNI (указать домен), ALPN (выбрать протокол — h2/http/1.1), key_share (эфемерный DH), supported_versions, supported_groups, signature_algorithms.

### Вопрос 3. Как WebSocket апгрейдится из HTTP?

Клиент отправляет обычный HTTP/1.1 GET, но со специальными заголовками:

```
GET /ws/stats HTTP/1.1
Host: <YOUR_DOMAIN>
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: <случайные 16 байт, base64>
Sec-WebSocket-Version: 13
```

Сервер, увидев `Upgrade: websocket`, отвечает:

```
HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: <base64(SHA1(client_key + magic))>
```

где magic = `258EAFA5-E914-47DA-95CA-C5AB0DC85B11`.

После 101 TCP-коннекшн перестаёт быть HTTP. По нему идут WebSocket-фреймы (FIN+opcode+mask+len+payload). Оба конца независимо отправляют text/binary/ping/pong/close.

В нашем проекте между клиентом и FastAPI стоит nginx, и в конфиге нужно явно:

```nginx
proxy_http_version 1.1;
proxy_set_header Upgrade $http_upgrade;
proxy_set_header Connection "upgrade";
```

Без этого Upgrade-заголовок не проходит до FastAPI.

### Вопрос 4. В чём разница между HTTP/1.1 и HTTP/2?

| Аспект | HTTP/1.1 | HTTP/2 |
|---|---|---|
| Формат | текстовый | бинарный (frames) |
| Мультиплексирование | нет (pipelining не прижился) | да, десятки streams в одном TCP |
| Head-of-line blocking | на уровне HTTP | только на уровне TCP |
| Сжатие заголовков | нет | HPACK |
| Приоритеты | нет | PRIORITY-фреймы |
| Server push | нет | да (редко используется) |
| Двоичные данные | `Content-Length`/chunked | DATA-frames |
| Keep-alive | по умолчанию | всегда |

Главное отличие — мультиплексирование: один TCP несёт много параллельных запросов без blocking, что сильно ускоряет загрузку страниц с десятками ресурсов.

### Вопрос 5. Что такое SNI?

SNI (Server Name Indication, RFC 6066) — расширение TLS, в котором клиент в открытом ClientHello передаёт имя домена, к которому он подключается. Это нужно для виртуального хостинга: когда на одном IP живут несколько HTTPS-сайтов с разными сертификатами, без SNI сервер не знает, какой сертификат отдать.

**Что видит ISP:** SNI передаётся *до* шифрования, в cleartext. Это основной канал утечки имени домена. Encrypted Client Hello (ECH) — экспериментальное расширение TLS 1.3, шифрует SNI.

**В нашем проекте** Reality использует SNI для маскировки: VPN-клиент кладёт в ClientHello `SNI: <MASKED_SNI_HOST>`, и для ISP это выглядит как обычный HTTPS к <MASKED_SNI_HOST>.

### Вопрос 6. Зачем сертификат, если можно просто обменяться ключами?

Без сертификата мы решаем только половину задачи — конфиденциальность, но не аутентичность. Если просто обменяться публичными ключами по сети:

1. Man-in-the-Middle атакует handshake: подменяет ключ клиента на свой, ключ сервера — на свой. Теперь он дешифрует трафик, пересылает, снова шифрует.
2. Клиент не может проверить, что публичный ключ принадлежит именно тому серверу, с которым он хочет общаться.

Сертификат решает это: он содержит публичный ключ + имя сервера, подписанный доверенным CA. Клиент проверяет цепочку подписей до корневого CA, который у него в trust-store. Если подписи валидны и имя совпадает — значит, CA подтвердил, что этот ключ принадлежит этому серверу.

Без CA-инфраструктуры пришлось бы:
- обмениваться ключами по out-of-band каналу (QR-код, SMS);
- вручную «привязывать» ключ (pinning);
- полагаться на TOFU (trust on first use) — первое соединение уязвимо.

### Вопрос 7. Что такое ARP?

ARP (Address Resolution Protocol, RFC 826) — протокол канального уровня, разрешающий IP-адрес в MAC-адрес в локальной сети. Работает только в пределах broadcast-домена (обычно — одна Ethernet/WiFi-сеть).

**Как работает:**

1. Хост хочет отправить пакет на 192.168.1.10, не знает MAC.
2. Broadcast'ит ARP-запрос: «У кого 192.168.1.10? Ответьте 00:11:22:AA:BB:CC».
3. Владелец 192.168.1.10 отвечает unicast: «Мой MAC 44:55:66:DD:EE:FF».
4. Запрашивающий кэширует в ARP-таблице на ~минуту.

**В проекте:** когда клиент отправляет пакет на `<YOUR_VPS_IP>`, его ОС проверяет: адрес в моей подсети? Нет — значит, надо отправить на default gateway. ARP для MAC шлюза → отправляем пакет туда. Дальше пакет идёт по BGP.

**Атаки:** ARP spoofing (MITM в LAN), защита — статические ARP-таблицы или DHCP snooping.

### Вопрос 8. Что если твой VPS упадёт?

Сценарии и последствия:

1. **Kratkaya недоступность (~минуты).** VPN-клиенты теряют TLS-соединение, пытаются переподключиться. Как только VPS поднимется — всё восстанавливается.
2. **Долгая недоступность (часы).** Админка недоступна, бот перестаёт отвечать, VPN не работает. Пользователи жалуются.
3. **Полный отказ (диск умер, IP-отозван).** Восстановление из бэкапа на новом VPS. Процедура:
   - поднять новый VPS;
   - восстановить `/etc/letsencrypt/`, `/usr/local/etc/xray/config.json`, `/opt/xray-bot/bot.db`, `/etc/nginx/*.conf`;
   - сменить IP в DNS A-записи `<YOUR_DOMAIN>`;
   - раздать новые share-линки клиентам (IP в них).

**SPOF (single point of failure).** У нас один VPS. Решения:
- HA-пара (второй VPS как cold/warm standby);
- мультирегион с DNS failover (Route53 health check);
- горизонтальное масштабирование Xray через loadbalancer (задача большая).

**Бэкапы.** Текущая практика — ручное сохранение конфига в git. Автоматический бэкап бота (`bot.db`) — по cron в S3 или на второй сервер.

### Вопрос 9. Как защититься от DDoS?

DDoS — заваливание сервиса трафиком с множества источников. Уровни:

**L3/L4 (SYN flood, UDP flood, amplification):**
- cloud-based scrubbing (Cloudflare, AWS Shield);
- rate-limiting на уровне firewall (iptables, nftables);
- SYN cookies (`net.ipv4.tcp_syncookies = 1`);
- ограничение connection rate per IP.

**L7 (HTTP flood, slowloris):**
- nginx `limit_req_zone` — rate limit per IP;
- nginx `limit_conn_zone` — ограничение параллельных коннектов;
- таймауты (`client_body_timeout`, `send_timeout`);
- fail2ban на основе лога nginx;
- WAF (ModSecurity, Cloudflare).

**В нашем проекте** нет встроенной защиты от DDoS — полагаемся на хостера + скромный размер (никому не интересны). Если проект вырастет, первый шаг — поставить перед публичным входом Cloudflare (но это не совместимо с Reality, потому что Cloudflare терминирует TLS).

### Вопрос 10. Что такое NAT и как он влияет на проект?

NAT (Network Address Translation) — механизм, при котором маршрутизатор подменяет исходный IP-адрес пакетов, идущих наружу. Обычно используется SNAT с PAT (Port Address Translation) — один публичный IP «маскирует» много приватных.

**Пример (домашний роутер):**

```
телефон (192.168.1.100:45678)  ──►  роутер  ──►  <YOUR_VPS_IP>:443
                                       │
                              NAT-таблица:
                              192.168.1.100:45678 ↔ <external_IP>:58000
```

Обратный пакет на `<external_IP>:58000` роутер направляет на `192.168.1.100:45678`.

**Как влияет на проект:**

1. **Долгоживущие соединения рвутся.** NAT-таблица истекает по таймауту (30-300 секунд для TCP idle, 30 для UDP). Наш WebSocket с heartbeat 30 секунд — ровно решение этой проблемы. Без пинга админка через 5 минут тишины получала бы «connection lost».

2. **Бот не может получать входящие коннекты.** Это *плюс* для long-polling (не нужен public IP), *минус* для webhook (нужен).

3. **CGNAT у мобильных операторов.** Даже наружу выходящий трафик с 192.168.*.* превращается в shared IP у 100+ абонентов. Никакого входящего, даже если домашний роутер настроил port forwarding.

4. **VPN туннель преодолевает NAT.** VPN-клиент инициирует TCP-коннект на 443 → NAT пропускает → дальше трафик идёт в туннеле, NAT не мешает.

### Вопрос 11. Что видит ISP (провайдер)?

Для соединения с Reality-VPN:

**ISP видит:**
- IP-пакеты: источник (абонент), назначение `<YOUR_VPS_IP>:443`;
- TCP-пакеты: SYN/ACK, размеры;
- TLS ClientHello: SNI `<MASKED_SNI_HOST>`, cipher_suites (Chrome fingerprint), key_share;
- TLS Application Data: зашифрованные байты;
- объём трафика, тайминги.

**ISP НЕ видит:**
- содержимое прикладных данных (VLESS inside TLS);
- имя реального destination (YouTube, etc);
- факт, что это VPN (фингерпринт и сертификат как у <MASKED_SNI_HOST>).

Для соединения с админкой (без VPN):

**ISP видит:**
- SNI `<YOUR_DOMAIN>`;
- сертификат Let's Encrypt для этого домена;
- объём трафика;
- всё содержимое зашифровано TLS 1.3.

### Вопрос 12. Почему TCP, а не UDP для WebSocket?

WebSocket по стандарту (RFC 6455) определён только поверх TCP. Это встроено в протокол: handshake — HTTP Upgrade, требующий упорядоченного потока. Фреймы WS предполагают, что транспорт надёжный — они сами не имеют retransmit, sequence, FEC.

Если попробовать «положить WS на UDP» — нужно пересобрать всё: retransmit, ordering, flow control, congestion control. Получится своя версия QUIC. Эта работа сделана, но называется **WebTransport** — отдельный протокол поверх QUIC/HTTP/3, с другой семантикой.

Кроме того: TCP keep-alive / пара с прикладным heartbeat надёжно работает через NAT; UDP со своим keep-alive — хрупче.

### Вопрос 13. Как устроен Wireshark и как посмотреть свои пакеты?

Wireshark — графический анализатор сетевых пакетов. Использует libpcap (на Linux) или npcap (на Windows). Работает так:

1. **Capture phase.** Устанавливает сетевой интерфейс в promiscuous mode (принимает все пакеты, не только предназначенные ему). Читает raw-frames с интерфейса через `AF_PACKET` socket (Linux).
2. **Dissection phase.** Парсит каждый пакет по слоям: Ethernet → IP → TCP → TLS → HTTP. Каждый слой в отдельном dissector'е.
3. **Display.** Показывает дерево полей, фильтры (`http.request.method == GET`), summary-столбцы.

**Как посмотреть свои пакеты:**

```bash
# На VPS
tcpdump -i any -s 0 -w /tmp/capture.pcap port 443 and host <client_ip>

# Скачать локально, открыть в Wireshark
scp root@vps:/tmp/capture.pcap .
wireshark capture.pcap
```

**Про TLS.** Если нужно заглянуть *внутрь* TLS, нужен симметричный сессионный ключ. Два способа:
1. `SSLKEYLOGFILE` — браузер/Xray в debug-режиме пишет ключи в файл, Wireshark их подтягивает.
2. MITM-прокси с заменой сертификата (mitmproxy, но клиент должен доверять подставному CA).

**В нашем проекте** Wireshark полезен для:
- проверки, что админка действительно через TLS 1.3 (поле Version в handshake);
- анализа, видно ли SNI `<MASKED_SNI_HOST>` при VPN-подключении;
- отладки, почему WebSocket не апгрейдится (сравнение заголовков).

### Вопрос 14. Что такое HTTP/3?

HTTP/3 (RFC 9114) — новая версия HTTP, работающая поверх QUIC (RFC 9000). QUIC — транспортный протокол на UDP, со встроенным TLS 1.3.

**Ключевые фичи:**

1. **UDP-based транспорт** → никакого TCP head-of-line. Потеря пакета блокирует только тот stream, которому пакет принадлежит.
2. **Встроенный TLS 1.3.** Нет отдельного TLS-handshake, всё внутри QUIC. 1-RTT или 0-RTT.
3. **Connection migration.** Клиент может сменить IP (например, Wi-Fi → LTE), соединение сохраняется по connection ID.
4. **Мультиплексирование streams** как в HTTP/2, но без HOL.

**В нашем проекте HTTP/3 не используется**, потому что:
- наружный путь — HTTP/2 поверх TCP (надёжный, стабильный, Reality маскирует под TCP TLS);
- nginx mainline получил HTTP/3 поддержку недавно и она экспериментальна;
- выгода для маленькой админки минимальна.

### Вопрос 15. Объясни HPACK

HPACK (RFC 7541) — алгоритм сжатия HTTP-заголовков для HTTP/2. Мотивация: в HTTP/1.1 каждый запрос повторяет `User-Agent`, `Accept`, `Cookie` и т.п. — это десятки, сотни байт на каждый запрос.

**Как работает HPACK:**

1. **Статическая таблица** — 61 предопределённый entry наиболее частых заголовков:
   ```
   1:  :authority
   2:  :method = GET
   3:  :method = POST
   4:  :path = /
   5:  :path = /index.html
   6:  :scheme = http
   7:  :scheme = https
   8:  :status = 200
   ...
   ```
2. **Динамическая таблица** — кольцевой буфер (обычно 4KB), в который добавляются заголовки из предыдущих запросов. Обе стороны её синхронизируют.
3. **Huffman-кодирование** — для строковых значений используется static Huffman-таблица, даёт ~20% экономии.

**Кодирование заголовка:**
- Indexed Header Field: просто индекс в таблице (1 байт на `:method=GET`).
- Literal Header Field with Incremental Indexing: пара имя+значение, добавляется в динамическую таблицу.
- Literal without Indexing: пара, но не добавляется (для чувствительных — Authorization).
- Literal Never Indexed: то же + флаг «никогда не кодируй».

**Пример.** Первый запрос: отправляется полный `user-agent: Mozilla/5.0 (...)` + индексируется. Второй запрос того же клиента — ссылается на индекс (1-2 байта).

**Атака CRIME/BREACH в HTTP/1.1 с gzip-сжатием** (когда секрет заголовка + guessable plaintext сжимаются вместе — утечка по размеру) в HPACK частично митигируется через `Never Indexed`, но сохраняется риск — поэтому чувствительные поля не индексируют.

### Вопрос 16. Что такое Keep-Alive?

Два разных термина:

**1. TCP keep-alive** — периодические пустые пакеты для проверки живости TCP-коннекшна. Настраивается через сокет-опции `SO_KEEPALIVE` и `/proc/sys/net/ipv4/tcp_keepalive_*`. По умолчанию на Linux — 2 часа простоя до первой пробы.

**2. HTTP keep-alive (persistent connection)** — когда после HTTP-запроса соединение не закрывается, а переиспользуется для следующих запросов. Управляется заголовком `Connection: keep-alive` (в HTTP/1.0 по умолчанию выключено, в HTTP/1.1 включено по умолчанию). Это не то же самое, что TCP keep-alive — здесь нет пингов, просто не закрывается.

В нашем проекте:
- nginx → FastAPI использует HTTP keep-alive (пул соединений);
- WebSocket реализует собственный heartbeat (JSON ping/pong);
- TCP keep-alive задействован опосредованно через ОС.

### Вопрос 17. Как работает certificate pinning и у тебя он есть?

Certificate pinning — когда клиент «жёстко привязывает» ожидаемый сертификат/ключ сервера. Обычная TLS-проверка доверяет любому сертификату, подписанному любым trusted CA. При pinning'е клиент говорит: «я принимаю только вот этот конкретный сертификат/публичный ключ/SPKI».

**Варианты:**
- **Cert pinning** — хэш конкретного сертификата.
- **Public key pinning** — хэш публичного ключа (чаще; сертификат меняется, ключ может оставаться).
- **SPKI pinning** — Subject Public Key Info hash.

**Защита от:**
- скомпрометированного CA (если какой-то CA выдал злоумышленнику сертификат на наш домен — клиент не примет);
- MITM корпоративного прокси (с подставным CA в доверенных).

**Реализация:**
- HPKP (HTTP Public Key Pinning, RFC 7469) — заголовок `Public-Key-Pins` в HTTP-ответе. **Deprecated**, браузеры убирают поддержку — слишком легко забанить свой собственный сайт навсегда.
- Certificate Transparency (CT) + OCSP stapling — современный подход через лог.
- Manual pinning в клиентах (мобильные приложения через OkHttp/TrustKit и т.д.).

**В нашем проекте pinning'а нет.** Админка работает в браузере, браузеры не поддерживают HPKP. Если злоумышленник получит MITM-сертификат на наш домен — мы это не обнаружим. Защита — прежде всего в надёжности CA (Let's Encrypt с CT-log) и отсутствии слабых CA в trust-store пользователей.

Для Xray/Reality-подключения вопрос «pinning» не возникает: сертификат `<MASKED_SNI_HOST>` не проверяется нашим клиентом, Reality аутентифицирует сервер через публичный ключ Curve25519 в `shortIds` — это и есть функциональный аналог pinning'а на уровне протокола.

### Вопрос 18. Что такое CORS и зачем?

CORS (Cross-Origin Resource Sharing, RFC 6454 + recommendation) — механизм, расширяющий Same-Origin Policy (SOP) браузера. SOP запрещает JS со страницы `https://a.com` делать запросы (в том смысле, что *читать ответ*) к `https://b.com`. CORS даёт серверу способ разрешить определённые кросс-доменные запросы.

**Почему SOP нужна.** Без неё JS со злонамеренного сайта `evil.com`, открытого в браузере пользователя, мог бы из-под браузера делать запросы к `bank.com` с пользовательскими куками и читать ответы (переводить деньги, читать баланс).

**Как работает CORS:**

1. **Simple request** (GET/POST с стандартными Content-Type): браузер *отправляет* запрос, но *не даёт JS прочитать ответ*, если нет CORS-заголовков. Сервер возвращает `Access-Control-Allow-Origin: https://a.com` — браузер разрешает прочитать.

2. **Preflight** (нестандартные методы/заголовки): браузер сначала шлёт `OPTIONS`-запрос:
   ```
   OPTIONS /api/keys
   Origin: https://a.com
   Access-Control-Request-Method: DELETE
   Access-Control-Request-Headers: Authorization
   ```
   Сервер отвечает:
   ```
   HTTP/1.1 204 No Content
   Access-Control-Allow-Origin: https://a.com
   Access-Control-Allow-Methods: DELETE, POST
   Access-Control-Allow-Headers: Authorization
   Access-Control-Max-Age: 3600
   ```
   Только после этого браузер шлёт реальный DELETE.

**В нашем проекте** админка на одном origin (`<YOUR_DOMAIN>:4443`), CORS в минимуме. Если API будем открывать для сторонних — включим через FastAPI `CORSMiddleware`.

### Вопрос 19. Что такое mitmproxy?

mitmproxy — интерактивный HTTPS-прокси для отладки и анализа трафика. Работает как man-in-the-middle:

1. Клиент настроен ходить через прокси (HTTP_PROXY / system proxy).
2. Клиент делает CONNECT `example.com:443` — mitmproxy перехватывает.
3. mitmproxy от своего имени открывает TLS к example.com, получает настоящий сертификат.
4. mitmproxy генерирует *подставной* сертификат на example.com, подписанный собственным CA.
5. Клиент должен *доверять* CA mitmproxy (установить в системный trust-store). Без этого — ошибка сертификата.
6. Клиент устанавливает TLS с mitmproxy (видит подставной сертификат, но с валидной подписью от доверенного CA), mitmproxy — с example.com. Оба TLS расшифровываются внутри mitmproxy.

**Зачем:**
- дебаг мобильных приложений (увидеть API-запросы);
- проверка безопасности (SSL-pinning bypass);
- автоматизация (скриптуется на Python).

**Защита от mitmproxy:** certificate pinning (приложение проверяет конкретный сертификат, не CA). Именно поэтому банковские/защищённые приложения часто хардкодят SPKI.

**В нашем проекте** mitmproxy полезен для отладки WebSocket (смотреть JSON-обмен) или REST-API. VPN-трафик через mitmproxy не пройдёт, потому что Reality проверяет не сертификат, а Curve25519-ключ.

### Вопрос 20. Как работают порты? Можно ли слушать :80 от root и от обычного юзера?

Порты — 16-битное число (0-65535), идентифицирующее сокет внутри IP-хоста. Диапазоны:

- **0-1023 — Well-known / Privileged.** HTTP 80, HTTPS 443, SSH 22, DNS 53, и т.д. На Linux только root может bind'ить сокет на такой порт (POSIX capability `CAP_NET_BIND_SERVICE`).
- **1024-49151 — Registered.** IANA-зарегистрированные, но bind'ит любой пользователь.
- **49152-65535 — Dynamic/Ephemeral.** Для исходящих соединений (source port), автоматически выделяются ОС.

**Как обычный юзер может слушать :80:**

1. **Через capability:**
   ```
   setcap 'cap_net_bind_service=+ep' /usr/bin/python3
   ```
   Теперь Python может bind'иться на low-port без root.

2. **Через systemd:**
   ```ini
   [Service]
   AmbientCapabilities=CAP_NET_BIND_SERVICE
   ```

3. **Через iptables REDIRECT:**
   ```
   iptables -t nat -A PREROUTING -p tcp --dport 80 -j REDIRECT --to-ports 8080
   ```
   Юзер слушает 8080, приходящий трафик на 80 перенаправляется.

4. **Unprivileged port start** (Linux 4.11+):
   ```
   sysctl net.ipv4.ip_unprivileged_port_start = 80
   ```

**В нашем проекте** nginx запускается как systemd-service через root (нужен для bind 80/4443/443), далее drop'ает privileges до `nginx` user. Это стандартный pattern.

### Вопрос 21 (бонус). Что такое MTU и PMTU Discovery?

MTU (Maximum Transmission Unit) — максимальный размер Ethernet-фрейма, типично 1500 байт. Если IP-пакет больше MTU на пути — он либо фрагментируется (медленно, неэффективно), либо отбрасывается с ICMP Fragmentation Needed.

**PMTU Discovery** — автоматический механизм: ОС отправляет пакет с DF-bit (don't fragment), ловит ICMP Fragmentation Needed с указанием «следующий хоп имеет MTU X», уменьшает свой MSS.

**В проекте это важно для VPN-туннелей.** Внутренний пакет + обёртки (TLS + Reality + VLESS) могут превысить MTU. Xray обычно сам подбирает MSS, но если ICMP блокируется где-то на пути — PMTU сломан, пакеты просто пропадают, создавая ощущение «VPN работает медленно».

### Вопрос 22 (бонус). Что такое TLS 1.3 0-RTT и почему его опасно включать?

0-RTT позволяет клиенту послать прикладные данные в первом же flight'е к серверу, используя pre-shared key (PSK) от предыдущей сессии. Выигрыш — 1 RTT экономится на повторных подключениях.

**Опасность — replay attack.** Злоумышленник может записать 0-RTT-данные и переиграть их — сервер примет как валидные. Защита:
- использовать 0-RTT только для идемпотентных запросов (GET без побочных эффектов);
- anti-replay cache на сервере (ограниченное время).

В nginx включается через `ssl_early_data on`. У нас **выключено** — меньше поверхность атаки, без заметной потери скорости.

### Вопрос 23 (бонус). Почему ты не используешь WireGuard?

WireGuard — современный VPN-протокол, быстрее и проще OpenVPN. Преимущества:
- маленький код (~4000 строк, легко аудитить);
- производительность (в ядре Linux);
- ChaCha20-Poly1305, Curve25519 — современная криптография.

**Почему не у нас:**
- WireGuard работает по UDP — заметен для DPI как «UDP с высокой энтропией», статистически не похож на HTTPS;
- протокол без обфускации, есть отпечатки;
- для целей traffic pattern obfuscation нужен TLS-like стек — Reality решает это на другом уровне.

Для корпоративного VPN (site-to-site, с разрешённым UDP) WireGuard — лучший выбор. Для нашего кейса — TCP+TLS важнее производительности.

### Вопрос 24 (бонус). Как обеспечивается безопасность пароля администратора?

В проекте авторизация админки может идти через JWT (токены) или через логин+пароль. Для паролей:

1. **Не хранить в plaintext.** Хэшировать argon2id / bcrypt с индивидуальной солью.
2. **Длинная соль** — защита от rainbow tables.
3. **Memory-hard функция** — защита от GPU-атак.
4. **Constant-time сравнение** хэшей.
5. **Rate-limit на login** — защита от перебора.
6. **MFA** — второй фактор (TOTP через Google Authenticator).

Параметры argon2id: time=3, memory=64MB, parallelism=4 — компромисс между безопасностью и производительностью на login.
